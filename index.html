01 The Fuzzing Loop

Modern fuzzers iterate on a tight feedback loop — every stage has an assumption an attacker can break.

  • SEED starting inputs
  • MUTATE bit-flips, splicing, dictionaries
  • EXECUTE observe crashes & hangs
  • COVERAGE new edges → keep input

02 Why Anti-Fuzzing?

1

Fuzzing found 100s of CVEs

AFL, libFuzzer, honggfuzz have become standard attacker tools.

2

Defenders can't always patch fast

Legacy binaries, closed-source vendors, embedded devices.

3

What if we slowed attackers down?

Raise fuzzing cost without changing program behavior.

→ FUZZIFICATION: make binaries fuzz-hostile, user-friendly.

03 Threat Model

DEFENDER

  • Owns source code
  • Compiles hardened binary
  • Ships to users

ATTACKER

  • Has the binary
  • Full fuzzing toolkit
  • Unlimited compute

Goal: normal users see no slowdown. Fuzzers see walls.

04 Three Techniques

A

SpeedBump

Attacks: throughput

Insert delays on cold paths that fuzzers hit far more often than users.

B

BranchTrap

Attacks: coverage feedback

Explode the branch space so coverage-guided fuzzers drown in edges.

C

AntiHybrid

Attacks: symbolic execution

Inject constraints that choke concolic/hybrid fuzzers.

04.A SpeedBump

Slow down rarely-executed paths.

  • Profile with benign inputs
  • Mark cold blocks
  • Inject delay loops / junk work

User hits these paths <1% of the time.
Fuzzer hits them constantly. 

// cold block — injected delay
if (unlikely_branch) {
  for (int i = 0; i < N; i++) {
    volatile uint64_t x = rand();
    x = x * 0x9e3779b97f4a7c15ULL;
  }
  original_cold_code();
}

04.B BranchTrap

Flood coverage with fake edges.

  • Coverage-guided fuzzers reward new edges
  • Insert many equivalent branches keyed on input
  • Fuzzer thinks it's progressing — it isn't

Raises the coverage bitmap entropy to hide real edges. 

// fake branches explode edge count
switch (input[i] & 0xFF) {
  case 0x00: sink ^= 0x1a; break;
  case 0x01: sink ^= 0x2b; break;
  // ... 254 more cases
  case 0xFF: sink ^= 0xc3; break;
}
// all produce same observable behavior

04.C AntiHybrid

Poison the symbolic executor.

  • Hybrid fuzzers use SMT to solve hard constraints
  • Insert hash comparisons / crypto-like ops
  • Solver times out — fuzzer falls back to blind mutation
// cheap to run, brutal to solve
uint32_t h = input_hash;
for (int i = 0; i < 8; i++)
  h = ((h << 5) + h) ^ input[i];
if (h == MAGIC) trigger_real_path();
// SMT solvers cannot invert this cheaply

06 Take-Away

Fuzzing assumes the binary is neutral ground.
FUZZIFICATION shows it doesn't have to be.
  • Anti-fuzzing is the dual of fuzzing: attack each stage's assumption.
  • Cost-asymmetry between benign user and adversarial fuzzer is exploitable.
  • Ethics: same techniques protect benign code and malware — open question.

07 Unclear Content

  • Profiling coverage: How representative is the "benign input" profile? Could an adversary craft legitimate-looking inputs that hit cold paths?
  • BranchTrap vs. modern fuzzers: Do newer edge-count-normalizing fuzzers (e.g., with context- sensitive coverage) defeat BranchTrap? The paper's evaluation predates some of these.
  • Composition order: When all three techniques compose, does the user-side overhead stay sub-linear, or do delays stack multiplicatively?
